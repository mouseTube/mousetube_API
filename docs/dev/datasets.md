# Datasets

A dataset is a set of recording sessions; the page shows the files of those sessions.

- **Metadata JSON (public):** `GET /api/dataset/<id>/metadata/` gives one dataset, `GET /api/dataset/metadata/` all of them. It lists the sessions with protocol, laboratory, animals, equipment, references and files (DOI, repository). Contact e-mails are never included.
- **Add a dataset (admins only):** in the admin, *Mousetube_Api > Datasets > Add*, or on the website, page *Dataset*, button *Add a dataset*. The API (`POST /api/dataset/`) refuses everyone else.
- **Change or delete a dataset (admins only):** on the page *Dataset*, the pencil edits the name, the description and the sessions (`PATCH /api/dataset/<id>/` with `recording_session_ids`), the bin deletes it after a confirmation (`DELETE`). A file belongs to its session, so adding a session adds all its files and taking it out removes them from the dataset only: the sessions and files stay in the vocalizations. Deleting a dataset removes nothing else.
- **What visitors see:** only the sessions that are *shared* or *published*. A draft put in a dataset by an administrator stays private (in the page and in the metadata JSON) until it is shared; administrators see everything.
- **Images of a file (admins only):** each file of the page has a spectrogram and a plot. The button on its row sets, replaces or removes them (`POST` / `DELETE /api/file/<id>/images/?field=plot`), whoever created the file; they must be real images (PNG, JPEG, WebP), 10 MB at most. A box *Also send these images to Zenodo* (unticked by default) puts them in the record when the session is published, see [published sessions](publication.md).
- **Files of a Zenodo record (public):** `GET /api/file/<id>/zenodo-files/` gives the name, the size and the download address of each file of the record a file belongs to (the recording, the tables of the detection tools, the images), so that the page can offer each one. Only files the user may see; only `zenodo.org` and `sandbox.zenodo.org`. The list is kept an hour and Zenodo is asked at most 60 times a minute: **429** beyond, **502** when Zenodo does not answer, **404** for a file Zenodo does not hold.
- **Zip of a dataset or of a record (signed-in users):** Zenodo no longer gives `.../files-archive` to programs, so mouseTube makes the zip. `POST /api/dataset/<id>/download/` with `{"scope": "sound"}` (the file of each row) or `{"scope": "all"}` (the default: every file of the Zenodo record of each row, one folder per record) checks what the user may see and gives a **token**; `GET` the same address with `?token=` within two minutes, **once**, sends the zip. A link cannot carry the JWT of the login, hence the token, which also holds the scope and cannot be changed. `POST /api/file/<id>/record-download/` does the same for every file of one record. The zip holds what the Dataset page shows to the user (a draft is shown to the administrators only).
- **How the zip is made:** while it is sent, one file after the other: nothing is written on the server, so there is no disk space to count (a publication at the same time does not compete for it) and nothing is left when a download is cut. One download per user and `DATASET_ZIP_PARALLEL` at once on the server (**429**), limits on the files and the bytes checked before it starts (**413**, see [configuration](configuration.md)); a file that cannot be read is listed in `_errors.txt` in the zip. The asynchronous server (gunicorn with uvicorn) sends it as it goes; the development server (`runserver`) builds the whole zip in memory first, so do not try a big dataset there.
