# Jeux de données

Un jeu de données est un ensemble de sessions d'enregistrement ; la page montre les fichiers de ces sessions.

- **JSON de métadonnées (public) :** `GET /api/dataset/<id>/metadata/` donne un jeu, `GET /api/dataset/metadata/` tous. Il liste les sessions avec protocole, laboratoire, animaux, matériel, références et fichiers (DOI, dépôt). Les e-mails des contacts ne sont jamais inclus.
- **Ajouter un jeu (administrateurs seulement) :** dans l'admin, *Mousetube_Api > Datasets > Add*, ou sur le site, page *Dataset*, bouton *Add a dataset*. L'API (`POST /api/dataset/`) refuse tous les autres.
- **Modifier ou supprimer un jeu (administrateurs seulement) :** sur la page *Dataset*, le crayon modifie le nom, la description et les sessions (`PATCH /api/dataset/<id>/` avec `recording_session_ids`), la corbeille le supprime après confirmation (`DELETE`). Un fichier appartient à sa session : ajouter une session ajoute tous ses fichiers et la retirer les enlève du jeu seulement : les sessions et les fichiers restent dans les vocalisations. Supprimer un jeu ne retire rien d'autre.
- **Ce que voient les visiteurs :** seulement les sessions *shared* ou *published*. Un brouillon placé dans un jeu par un administrateur reste privé (dans la page et dans le JSON de métadonnées) jusqu'à son partage ; les administrateurs voient tout.
- **Images d'un fichier (administrateurs seulement) :** chaque fichier de la page a un spectrogramme et une courbe. Le bouton de sa ligne les met, les remplace ou les retire (`POST` / `DELETE /api/file/<id>/images/?field=plot`), quel que soit le créateur du fichier ; ce doivent être de vraies images (PNG, JPEG, WebP), 10 Mo au plus. Une case *Also send these images to Zenodo* (décochée par défaut) les met dans la notice quand la session est publiée, voir [sessions publiées](publication.md).
- **Fichiers d'un enregistrement Zenodo (public) :** `GET /api/file/<id>/zenodo-files/` donne le nom, la taille et l'adresse de téléchargement de chaque fichier de l'enregistrement auquel appartient un fichier (l'enregistrement, les tableaux des outils de détection, les images), pour que la page propose chacun. Seulement les fichiers que l'utilisateur peut voir ; seulement `zenodo.org` et `sandbox.zenodo.org`. La liste est gardée une heure et Zenodo est interrogé au plus 60 fois par minute : **429** au-delà, **502** quand Zenodo ne répond pas, **404** pour un fichier que Zenodo n'héberge pas.
- **Zip d'un jeu de données ou d'un enregistrement (utilisateurs connectés) :** Zenodo ne donne plus `.../files-archive` aux programmes, donc mouseTube fabrique le zip. `POST /api/dataset/<id>/download/` avec `{"scope": "sound"}` (le fichier de chaque ligne) ou `{"scope": "all"}` (par défaut : tous les fichiers de l'enregistrement Zenodo de chaque ligne, un dossier par enregistrement) vérifie ce que l'utilisateur peut voir et donne un **jeton** ; un `GET` sur la même adresse avec `?token=` dans les deux minutes, **une seule fois**, envoie le zip. Un lien ne peut pas porter le JWT de la connexion, d'où le jeton, qui contient aussi le choix et ne peut pas être modifié. `POST /api/file/<id>/record-download/` fait de même pour tous les fichiers d'un enregistrement. Le zip contient ce que la page Dataset montre à l'utilisateur (un brouillon n'est montré qu'aux administrateurs).
- **Comment le zip est fabriqué :** pendant qu'il est envoyé, un fichier après l'autre : rien n'est écrit sur le serveur, donc pas d'espace disque à compter (une publication en même temps ne le concurrence pas) et rien ne reste quand un téléchargement est coupé. Un téléchargement par utilisateur et `DATASET_ZIP_PARALLEL` à la fois sur le serveur (**429**), des limites sur les fichiers et les octets vérifiées avant de commencer (**413**, voir la [configuration](configuration.md)) ; un fichier illisible est listé dans `_errors.txt` dans le zip. Le serveur asynchrone (gunicorn avec uvicorn) l'envoie au fur et à mesure ; le serveur de développement (`runserver`) fabrique d'abord tout le zip en mémoire : n'y essayez pas un gros jeu de données.
